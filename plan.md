# Porting Plan

Goal: run The Faery Tale Adventure natively on Linux using Rust, with the original C logic reused
at first and ported to Rust gradually. Original source (reference) is in `faery-tale-amiga/`.

## What we're porting

- About 7,000 lines of Aztec C and 3,000 lines of 68000 assembly.
- Game data is included in `faery-tale-amiga/game/` (disk `image`, songs, fonts, palettes, pictures).
- Amiga-specific parts that must be replaced:
  - Graphics: custom chips, bitplanes, `BltBitMap`, hardware sprites, copper/viewports, palettes.
  - Disk: raw floppy reads via trackdisk (`hdrive.c` already has a file-based mode using `image`).
  - Sound: Amiga music driver (`gdriver.asm`).
  - Input and timing: Amiga input handling and vertical-blank interrupt.
- Data files are big-endian and the code assumes 32-bit pointers.

## Phases

Each phase should end with something that builds and runs.

### Phase 0 - Project setup
- [x] Install Rust, gcc, `libsdl2-dev`.
- [x] `cargo init`, add `sdl2`, `cc` and `bindgen` (if needed) dependencies.
- [x] Open an SDL window and draw a test pattern.
- [x] Write a small tool that dumps the layout of `game/image` so we understand the data.

### Phase 1 - Understand the code and data
- [x] Read `fmain.c` and list what it calls from the Amiga libraries (the main ones: `AllocMem`,
      `SetAPen`, `Read`, `Open`, `Text`, `SetRGB4`, `DoIO`, `BltBitMap`, `SetFont`, `LoadRGB4`).
- [x] Document the data file formats (`image`, `p1a`..`p3b`, `page0`, `songs`, `v6`, `winpic`,
      `hiscreen`, fonts).
- [x] Document the assembly routines in `fsubs.asm`, `fsupp.asm`, `MakeBitMap.asm` and
      `gdriver.asm`: what each one does and who calls it.
- [x] Write findings into `docs/` (first pass done; open questions listed at the end of each file).

### Phase 2 - Get the C compiling with gcc
- [x] Copy the C files into `csrc/` (`fmain.c`, `fmain2.c`, `iffsubs.c`, `hdrive.c`; the originals are untouched).
- [x] Add stand-in Amiga headers and types (`csrc/amiga.h`, `csrc/stubs/`) so the code compiles.
- [x] Replace the Aztec `.p` prototype files with `csrc/protos.h`, generated by `tools/genprotos.sh`.
- [x] `long` is made 32 bit (`#define long int` in `amiga.h`), `-fcommon` for Aztec-style globals.
- [x] Inline 68000 `#asm` blocks in `fmain2.c` are fenced off (`AMIGA_ASM_68K`); copy protection removed.
- [x] Everything compiles and links (`cd csrc && make`) with stubbed Amiga calls
      (`platform_stubs.c`) and stubbed assembly routines (`asm_stubs.c`). Running `build/fta_c`
      starts up, calls the stubs, and exits.
- [x] The game's own `rand` family is ported for real (it must replace libc `rand`).
- [ ] Still K&R style (old function definitions); builds only with `-std=gnu89`. Convert to
      modern definitions as modules move to Rust.
- [ ] Audit remaining 32-bit assumptions: pointers cast to ints (`ADDR`, font `seg<<2` hack in
      `open_all`), structs saved to disk, `sizeof` of structs that were laid out for the 68000.

### Phase 3 - Rust platform layer
Rust implements the Amiga calls the C code makes, exported with `extern "C"` from `src/platform/`.
(History) The C code was first built into the Rust binary by `build.rs`. There is no C in the build any more; `csrc/` is only the reference.
- [x] Memory: `AllocMem`/`FreeMem` (calloc/free), `AllocRaster`, `AvailMem`, `TypeOfMem`.
- [x] Files: `Open`/`Read`/`Write`/`Seek`/`Close`/`Lock` on normal files, case-insensitive paths
      (data dir `FTA_DATA`, default `faery-tale-amiga/game`; `dfN:` names go to `saves/`).
- [x] Disk: the game already reads blocks from the `image` file when it exists; the trackdisk
      calls are no-ops.
- [x] Bitmaps and rastports: planar bitmaps, `InitBitMap`, `MakeBitMap`.
- [x] Drawing: `BltBitMap` (plain copy only), `SetAPen`, `Move`, `Draw`, `RectFill`, `SetRast`,
      `ScrollRaster`, filled polygons.
- [x] Palette: `SetRGB4`, `LoadRGB4`, `GetRGB4`, `GetColorMap`.
- [x] Display: viewports are composed into a 640x200 frame and shown with SDL2 when the game
      calls `LoadView` (page flip), paced at 50 Hz. `FTA_SHOT=file.ppm FTA_SHOT_AFTER=n`
      saves a screenshot for testing without a screen (`tools/ppm2png.py` converts it).
- [x] Milestone: the intro story book (pictures and page flips) shows correctly.
- [x] Text: the story font `fonts/Amber/9` is loaded from the original file. Topaz 8 (an Amiga
      ROM font we do not have) is replaced by a fixed 8x8 stand-in font (`font8x8` crate).
- [x] Sprites: the mouse pointer sprite is drawn on top of the text panel; the system cursor is hidden.
- [x] Input: SDL keyboard and mouse feed the game's key ring buffer and mouse state
      (`csrc/input.c` replaces `HandlerInterface`, `getkey`, `decode_mouse`). Arrow keys walk
      (two arrows = diagonal), keypad digits work as on the Amiga, left mouse button walks
      toward the compass pointer and clicks menus, right mouse button or keypad 0 fights, Ctrl is
      the joystick fire button.
- [x] The riddle copy protection (typing words from the manual) is skipped.
- [x] Milestone: after the intro, the game's text panel, menu and compass show correctly. The map
      area is black until Phase 4 (map drawing is still stubbed).
- [ ] Left for later: joystick/gamepad, layer clipping for the witch's polygon, a real Topaz look-alike.
- Audio device: see Phase 5.

Test helpers (environment variables): `FTA_SHOT=file.ppm FTA_SHOT_AFTER=<ticks>` saves a screenshot
after that many 1/50 s ticks and quits; `FTA_INJECT="60:Space,200:Return"` presses keys at given
ticks; `FTA_SECONDS=n` quits after n seconds; `FTA_WATCHDOG=n` aborts if the game stops waiting
for frames for n seconds (use under gdb to find a stuck loop). When running a test with a
timeout use `timeout -s KILL`, SDL catches the normal termination signal.

### Phase 4 - Rewrite the assembly
Rewritten in C first (easy to compare with the original), moved to Rust later with the rest of
the game. Routines still stubbed are in `csrc/asm_stubs.c` and print "STUB called" when used.
- [x] Map and collision (`csrc/asm_map.c`): `px_to_im`, `prox`, `mapxy`, `genmini`, `newx`,
      `newy`, `wrap`, `map_adjust`, `page_det`.
- [x] Map drawing (`csrc/asm_map.c`): `map_draw`, `strip_draw`, `row_draw`, `scrollmap`
      (the blitter scroll is now `memmove`). Milestone: the world shows and scrolls when you walk.
- [x] IFF helpers: `ReadHeader`, `ReadLength`, `unpack_line` (`csrc/asm_port.c`), input (`csrc/input.c`),
      the game's random numbers (`rand`, `rnd`, ...).
- [x] Sprites (`csrc/asm_blit.c`): `make_mask`, `maskit`, `mask_blit`, `shape_blit`, `save_blit`,
      `rest_blit`, `clear_blit`. A small software blitter reproduces what the Amiga blitter did, so
      the original sprite code runs unchanged. Milestone: the hero shows, walks and animates.
- [x] Text and story (`csrc/asm_text.c`): `ssp`, `prdec`, `text`, `move`, `placard`,
      `placard_text`, `question`, `msg`, `event`, `speak`, `prq`, `cursor`. The story strings and
      tables from `narr.asm` (plus the title text and compass graphics from `fsubs.asm`) are
      converted to Rust data by `tools/narr2rs.py` into `src/game/data/story_text.rs`. Milestone: messages
      and the status line show in the panel.
- [x] `set_course` (enemy steering), `stuff_flag`, `bigdraw` (overview map), `do_error`.
- [ ] Still stubbed in `csrc/asm_stubs.c`: the music and sound routines (`init_music`,
      `playscore`, `setscore`, `stopscore`, `playsample`, `wrap_music`; Phase 5) and the Amiga
      input handler hooks (`HandlerInterface`, `trapper`), which are not needed.

### Phase 5 - Sound
- [x] Song and instrument formats worked out (`docs/data-formats.md`).
- [x] Music player in Rust (`src/platform/audio/`): an SDL audio callback runs the four-voice
      sequencer at 60 Hz (the vertical blank of the original) and mixes the four channels, with
      voices 1 and 4 on the left and 2 and 3 on the right as on the Amiga.
- [x] Sound effects: one-shot samples on voice 2, which pauses that music voice meanwhile.
- [x] Fixed a big-endian bug that made the game load no songs (`read_score`).
- [x] Test helper: `FTA_AUDIO_DUMP=file.wav` writes the mixed audio (with `FTA_SECONDS=n`).
- [ ] Checked by measuring the output (notes, harmonics, levels), not yet by ear. Things that may
      need tuning: overall volume, tempo (the original ran at the TV's 60 Hz or 50 Hz), and
      whether the Amiga's low-pass filter should be imitated.

### Phase 6 - First playable build
- [x] Title screen, intro, game start, map and scrolling.
- [x] Player moves, input works (keyboard and mouse).
- [x] Music and effects.
- [x] Save and load (`csrc/fmain2.c`, `sl_*`): rewritten to save field by field in big-endian
      order, so it no longer depends on how variables sit in memory. Files go to `saves/`
      (`A.faery` ...). Checked by saving after walking, then loading in a fresh run: the map area
      came out pixel-identical. Save files are the same size as the original's (about 1.2K).
- [ ] Combat, items, shops, dialogue, doors and caves: needs playtesting.
- [x] Sweep for leftovers of the 32-bit Amiga: grepped for pointer/int casts, raw struct reads
      and writes, and file reads; ran scripted sessions (walking, fighting, menus, intro) under
      AddressSanitizer. Found and fixed: the random seed was read as 64 bits (corrupting the next
      variable), and the menu key table was read one entry past its end. Nothing else showed up.
      (ASan build: `CFLAGS=-fsanitize=address RUSTFLAGS="-C link-arg=-Wl,--no-as-needed -C link-arg=-lasan"
      cargo build --target x86_64-unknown-linux-gnu`, run with `LD_PRELOAD=$(gcc -print-file-name=libasan.so)`.)
- [ ] Test helpers: `FTA_CLICK="tick:x:y,..."` clicks the left button (x in 0-319, y in screen
      lines); `FTA_INJECT` presses keys. Gameplay starts around tick 300, and the Game menu items
      are at x 225/250 and y 148 + 9 * row.
- [x] More test helpers (see `modern_engine_plan.md`, step 1): `FTA_STATE=file FTA_STATE_AFTER=tick`
      writes the game state as text (compare with `tests/state_regress.sh`);
      `FTA_CMD="tick:tp:x:y,tick:kill:luck"` teleports or kills the hero;
      `FTA_RECORD=file` logs input and `FTA_REPLAY=file` plays it back.

### Phase 7 - Port C to Rust
Superseded by `modern_engine_plan.md` (steps 2-4), which first cuts `main()` into functions and
gathers the state into structs, then ports the rules to Rust. Keep this list as a rough guide.
The current approach is `src/game/` (see section 4a of `modern_engine_plan.md`): `csrc/` stays untouched
and each file is ported into `src/game/`. Move modules one at a time, with the game runnable after each one. Rough order, easiest first:
- [x] `asm_port.c`, `input.c`, `iffsubs.c`, `hdrive.c`
- [x] `asm_blit.c`, `asm_text.c`, `asm_map.c`, `asm_stubs.c`
- [x] `fmain2.c` (functions and data tables)
- [ ] `fmain.c` (about 60% done; the remaining groups A-F are in `modern_engine_plan.md`, section 4a)

### Phase 8 - Polish
- [x] Window scaling and fullscreen, correct aspect ratio. (F11, resizable; gamepad added too)
- [x] Config file and key remapping.
- [x] Remove leftover Amiga stand-ins.
- [x] Packaging and how to supply game data.

### Phase 9 - Reusable engine (stretch goal)
Now planned in `modern_engine_plan.md` (two engines, four games: original, improved, remastered,
reimagined). This list is the older, more general version.
Turn the port into a modern engine that runs this game, and could run other games too.
- [ ] Split engine from game: world and tile map, scrolling, sprites and masking, input,
      audio, menus and text, save system go in an engine crate; the Faery Tale rules, item and
      enemy tables and story text stay in a game crate.
- [ ] Replace Amiga-shaped data in the engine with plain, documented types (RGB colors and
      chunky pixel buffers instead of 12 bit palettes and bitplanes) while still loading the
      original planar data files.
- [ ] Move game data (map regions, item tables, enemy tables, text) out of code into data files.
- [ ] Write documentation and a small example game on the engine, with its own placeholder assets.
- [ ] Keep the original game's assets out of the repo: players supply their own copy of the
      data files. The code is covered by the original author's MIT-style license, so keep their
      license notice and credit in the repo. The copyright status of the original game data is unclear.

## Risks

- The graphics code is tied to Amiga bitplanes and hardware tricks (split screens, sprites, copper
  colour changes). Some of it may need a redesign instead of a straight translation.
- The assembly has few comments and the author doesn't remember details, so we'll be reading it
  closely.
- Hidden 32-bit and big-endian assumptions will cause crashes and corrupt data.
- The legal status of the game data is unclear, so we shouldn't distribute it.
